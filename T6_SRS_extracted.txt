01 • INTRODUCTION
1. Introduction
1.1 Purpose
This Software Requirements Specification describes the expected behaviour, interfaces, data, quality attributes and acceptance conditions for the Intelligent Traffic Violation Reporting and Road Safety Management System. It is intended for the student development team, faculty guide, reviewers and test users. It establishes a shared baseline before Sprint 1 implementation.
1.2 Project background
Traffic violations and unsafe road behaviour can be difficult to report consistently when evidence, location and follow-up are scattered across channels. The proposed web application provides a structured mechanism for citizens to submit a report with an image and location, for authorised traffic personnel to review submissions, and for administrators to observe patterns in reports and accident-prone areas.
1.3 Objectives
Provide a simple citizen-facing process to submit a traffic-violation report with time, type, location and optional supporting evidence.
Create a reference number and transparent status history so a reporter can track their own submission.
Provide an authorised review workflow before a report is treated as verified or used to prepare an enforcement notice.
Support configurable offence rules and penalty values rather than embedding changeable amounts in program code.
Show aggregated, location-based patterns and summary analytics to help authorities identify potential road-safety hotspots.
Maintain access control, audit history and privacy boundaries appropriate to a student prototype handling potentially sensitive reports.
1.4 Intended audience and conventions
Requirements are labelled FR for functional requirements, NFR for non-functional requirements, BR for business rules and TC for test cases. “Must” indicates a requirement needed for acceptance; “should” indicates a recommended capability. IDs are stable references for discussions and tests.

02 • OVERALL DESCRIPTION
2. Overall product description
2.1 Product perspective
The system is a browser-accessible web application with a citizen portal, an officer review workspace and an administrator console. It uses PHP for server-side workflow and business logic, MySQL for persistent structured data, and HTML5, CSS3, JavaScript and Bootstrap for responsive user interfaces. A map provider and email/SMS delivery provider may be connected through replaceable adapters; the exact provider is a project decision, not fixed by the allocation sheet.
2.2 System boundary

2.3 High-level outcomes

2.4 Design principles
Human review before enforcement action; automated steps may assist but do not replace authorised decision-making.
Privacy by default: reporter details, exact evidence and vehicle identifiers are visible only to authorised users on a need-to-know basis.
Traceability: record important status transitions, rule changes and notice actions with actor and timestamp.
Accessible and responsive pages that remain usable on common desktop and mobile browsers.

02 • ROLES AND PERMISSIONS
3. User classes and access permissions
The role model below is the minimum proposed permission baseline. Administrative access must not be granted merely because a user knows a URL; permissions must be enforced on the server for every protected action.

3.1 Account requirements
Each account has a unique internal user ID and a verified unique email or approved login identifier.
Passwords are stored as salted hashes using a modern password-hashing function provided by the runtime; plaintext passwords are never stored or logged.
Role changes, account deactivation and password resets are restricted to approved workflows.
After repeated failed sign-in attempts, the system should apply rate limiting and may temporarily delay further attempts.
A user can sign out, and protected sessions expire after a configured period of inactivity.

05 • PROCESS MODELS
7. End-to-end report workflow

Figure 3. Proposed report-to-enforcement workflow. Legal/enforcement actions require authorised review.
7.1 Narrative process
Capture: the reporter enters a category, observed time, location and a concise description; optional vehicle information must be treated carefully.
Validate: the server validates required fields, time ranges, coordinate ranges, content type and file size. A rejected upload does not create a falsely successful submission.
Register: the system commits the report, evidence metadata and initial status together as far as practical, then returns a unique tracking reference.
Review: a permitted officer checks context and evidence. The system provides request-information, verify and reject actions and maintains history.
Notice: when a verified report maps to a valid offence rule, the system can create a draft. Issuance requires a permitted actor and confirmation of the rule and case state.
Learn: aggregated counts and coordinates can support hotspot analysis. The interface must distinguish citizen reports from verified outcomes and confirmed accidents.

06 • SYSTEM DESIGN
8. Proposed system architecture

Figure 5. Logical architecture using the assigned technology stack.
8.1 Component responsibilities

8.2 Key design decisions
Use prepared statements or a trusted database abstraction for all SQL involving user input.
Keep business rules in server-side services rather than duplicating them only in JavaScript.
Use random/unpredictable public tracking references that do not expose sequential internal database IDs.
Keep evidence storage references separate from public URLs; serve files only after access checks.
Use transactions when a state change must be recorded together with status history, notice data or audit entries.


06 • DATA MODEL
9. Logical data model

Figure 6. Simplified entity-relationship diagram; the cardinality summary appears beneath the model.
9.1 Core entities and relationships

9.2 Data integrity principles
Use foreign keys for the relationships that must not become orphaned.
Use unique constraints for login identifiers and public tracking references.
Store money using an exact decimal type, not floating point; store currency explicitly if multiple jurisdictions are possible.
Store latitude and longitude as decimal values with range checks; latitude must be -90 to 90 and longitude -180 to 180.
Store timestamps consistently (UTC on server/database is recommended) and format them for users in the configured time zone.
Avoid storing evidence binaries inside ordinary report text fields; use protected storage and metadata records.

08 • QUALITY AND SECURITY REQUIREMENTS
12. Non-functional requirements

12.1 Application security controls
Validate and normalise all input on the server; encode output according to its HTML/attribute/JavaScript context to reduce cross-site scripting risk.
Use CSRF tokens for state-changing browser forms and secure, HttpOnly, SameSite session cookies where supported.
Use password hashing, least privilege, session expiry, login rate limiting and secure error handling.
Upload checks: extension allow-list, actual MIME/content checks, size/count limits, random storage name, storage outside web root, access-control check on downloads.
Use prepared SQL statements; do not concatenate user input into queries or shell commands.
Protect configuration secrets; do not put DB passwords or API keys in source control.
Audit sensitive actions without logging passwords, tokens, raw uploaded content or unnecessary personally identifying information.

09 • RULES AND CONSTRAINTS
13. Business rules, assumptions and constraints
13.1 Business rules

13.2 Assumptions
Citizens and authority users have access to a browser and network connection.
The initial prototype has a limited set of manually maintained offence categories and rules.
Officer accounts are provisioned or approved by an administrator; open self-registration for enforcement roles is prohibited.
Any use of real personal data, vehicle identifiers or real enforcement action needs faculty and relevant authority approval.
Map and message provider credentials may not be available; the core application must degrade gracefully without them.
13.3 Constraints and dependencies
The required technology stack is PHP, MySQL, HTML5, CSS3, JavaScript and Bootstrap.
The student project schedule is short; prioritise report submission, review, tracking, core notices and a basic hotspot/dashboard flow before optional integrations.
The project sheet does not define jurisdiction-specific penalties, identity verification rules, payment processing or official police-system API access; these remain unconfirmed.
A real-world deployment would require secure hosting, operational monitoring, data governance and appropriate approval beyond a classroom demonstration.

ID | Quality attribute | Requirement / measurable target
NFR-001 | Performance | Under a representative student-demo load and indexed database, common page actions should usually complete within 3 seconds, excluding slow external map/notification providers. Measure during testing.
NFR-002 | Availability | For the academic prototype, deployment availability depends on the hosting environment; the team must document expected demo uptime and planned maintenance.
NFR-003 | Usability | A first-time tester should be able to submit a valid report without oral help, using clear labels, inline validation and a final review step.
NFR-004 | Compatibility | Core flows must be tested on at least one current Chromium-based browser and one additional supported browser or mobile viewport.
NFR-005 | Security | All non-local traffic carrying credentials or evidence uses HTTPS; role checks are server-side; SQL uses parameterised queries.
NFR-006 | Privacy | Collect only needed personal data; protect evidence; restrict case details; provide an approved retention approach before public deployment.
NFR-007 | Integrity | Status and notice transitions must validate allowed prior states and use transactions where related writes must be consistent.
NFR-008 | Auditability | Important decisions and configuration changes are timestamped and attributed to an actor; ordinary users cannot edit audit events.
NFR-009 | Maintainability | Separate presentation, workflow/service logic, database access and configuration; avoid hard-coded secrets and penalty values.
NFR-010 | Scalability | Filter and aggregate data server-side; paginate long queues and reports; add indexes based on observed query plans.
NFR-011 | Recovery | Document scheduled backups for MySQL and evidence storage; perform and record at least one restore test before final demo.
NFR-012 | Accessibility | Aim for keyboard operability, clear labels, contrast and text-based status indicators in all core workflows.
ID | Rule
BR-001 | A tracking reference is generated only for a submission accepted by server-side validation.
BR-002 | The report status can only change through the approved workflow; direct client-side status edits are ignored.
BR-003 | Only an authorised reviewer may verify or reject a report; a rejection requires a recorded reason.
BR-004 | A notice draft requires a verified report and an active offence rule applicable to the offence date and jurisdiction.
BR-005 | Issuing a notice requires an authorised role and a successful validation of case state, rule and amount.
BR-006 | Rule changes and notice cancellations/corrections must be attributable and auditable.
BR-007 | Hotspot counts must specify the selected period and data basis and must not imply causation.
BR-008 | Public views may show aggregated reports but must not disclose reporter identities or protected case evidence.
BR-009 | A possible duplicate is a review aid, not automatic proof that a report is false.
BR-010 | Date/time, currency, penalty and data-retention settings should be configurable rather than inferred from the server locale.
Explicit assumption  This SRS describes a student project prototype. It does not authorise actual enforcement, payment collection, surveillance or access to restricted governmental datasets.
